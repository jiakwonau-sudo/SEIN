## 3. 이번 최종 대조에서 수정한 결함

1. **내부 비용 입력 보호**: 미저장 변경을 모달 닫기·상세 탭 전환·다른 상세 열기·화면 이동 경고에 연결했다. 저장 중 행 삭제/추가 및 입력을 막고, 성공한 값만 저장 기준으로 갱신한다. 다른 창과의 버전 충돌 검사는 유지한다.
2. **상품→메일 이동**: 이동 확인 전에 상세창을 먼저 닫던 순서를 제거했다. 이동을 취소하면 원래 편집 내용을 유지하도록 하고, 이동 성공 시 상세창을 닫는다.
3. **견적 집계**: 과거 버전만 검색할 때 그 버전을 최신 예상액으로 오인하던 경로를 수정했다. 상단은 카테고리 전체의 최신 견적, 아래 목록은 검색·언어·통화 필터 기준임을 안내한다.
4. **일정 더 보기**: 월간 `+N개 일정` 클릭 시 해당 날짜를 지정한 목록으로 이동한다. 이전 개선 문서의 설명과 실제 구현이 일치하도록 보완했다.
5. **자료실 복원 상태**: 저장한 현재 폴더가 사라졌거나 다시 잠기면 루트로 이동한다. 깊은 폴더로 복귀할 때 조상 폴더를 펼치고, 기존 재클릭 접기는 유지한다. 업로드 중 제외 버튼·사진 단계 변경도 막는다.
6. **문서·제목**: 자료실 라우트의 브라우저 제목을 보완하고 README의 오래된 모바일 조회 전용 안내를 수정했다. 이 문서를 최신 인계 진입점으로 연결했다.

## 4. 실행 검증과 한계

- 수정 후 `npm run check`: **자동 테스트 59개 통과, Vite 빌드 성공**. 금액·권한·잠금·동시 저장 충돌·메일 초안·알림·PDF·XLSX·실제 HTTP 업로드/다운로드·ZIP·백업 무결성/실패/복원 검사를 포함한다.
- 이번 브라우저 검수는 `test-results/handoff-final-2026-09-23`의 별도 SQLite 샘플과 4193 포트에서 진행했다. 업무 DB나 실제 고객 자료로 저장 실험을 하지 않았다.
- 견적 v1=100만원, v2=200만원 샘플에서 v1만 검색해도 상단은 **최신 원화 공급가 200만원/영업 1건**, 목록은 v1 한 건으로 유지됨을 확인했다.
- 같은 날 일정 4개와 다른 날 일정 1개를 구성했다. `+1개 일정` 클릭 후 선택 날짜의 4개만 표시됨을 확인했다.
- 상품 내부 비용 `1200000+300000`을 저장해 150만원 표시, 다른 탭 방문 후 수식 보존, 저장 후 상품 메일 화면 이동과 상세창 종료를 확인했다.
- **미저장 경고의 취소/확인 버튼 실조작은 미완료**: 내장 브라우저가 native confirm 호출 단계에서 응답하지 않았다. 소스의 차단 분기와 저장 완료 후 이동은 확인했지만, 이를 취소·확인 모두 통과로 기록하지 않는다. Chrome/Edge에서 비용 수정→탭 전환/닫기/메일 이동→취소 시 값 보존, 확인 시 이동을 최종 확인해야 한다.
- 자료실 잠금/삭제 후 복원 및 업로드 중 버튼 제한은 코드 검토·빌드까지 확인했다. 이번 브라우저 재현 범위를 과장하지 않는다.
- 앞선 전체 화면 브라우저 검수·390×844 확인·성능 측정은 [9월 23일 개선 결과](점검_개선결과_2026-09-23.md)와 [실조작 기록](브라우저_실조작_검수기록.md)을 참고한다. 이 수치들은 운영 회선의 성능 보장이 아니다.

## 5. 실행·배포·데이터 구조

### 로컬 재실행

Node 24 이상에서 다음을 실행한다. 이미 설치된 작업본은 `npm start`로 재실행할 수 있다.

```powershell
npm ci
npm run check
npm start
```

접속: `http://localhost:4173`. 기본 검토 모드는 `127.0.0.1`에만 바인딩한다. 로컬 데이터는 `.local/sein.sqlite`, 첨부는 `.local/files`에 보존된다. `.env`를 사용하는 경우 현재 APP_MODE와 저장 위치를 먼저 확인한다. `--production`은 빌드 화면 제공 옵션이며, 그 자체로 운영 Supabase를 선택하지 않는다. `NODE_ENV=production`에서는 demo 모드 시작을 거부한다.

| `server/engine.mjs`, `server/missions.mjs` | 권한 검사와 업무 변경·버전 충돌 규칙 |
| `server/store.mjs`, `server/state-response.mjs` | SQLite/Supabase 저장, 권한 투영 후 증분 응답 |
| `shared/` | 금액·수식·반복·검색·업무 집계 공통 계산 |
| `scripts/`, `tests/` | 이관·백업·복원 도구 및 자동 검사 |
| `supabase/migrations/001_workspace.sql` | 서버 전용 JSONB 워크스페이스와 비공개 버킷 |

저장은 워크스페이스 한 행의 버전과 JSON 본문을 사용한다. 상품 ID↔영업 lines.equipmentId, 고객 ID↔영업 customerId, 견적 dealId↔영업, 파일 parentId/targetId↔폴더·업무 대상, 메모 targetType/targetId↔업무 대상을 연결한다. 회사 정보·사용자·권한·반복 일정·변경 이력도 이 본문에 들어간다. 첨부 바이너리는 별도 저장소에 둔다. 스냅샷과 이관 출처를 임의로 제거하면 과거 증빙·재현이 깨질 수 있다.

주요 API는 `/api/login`, `/api/state`, `/api/command`, `/api/upload`, `/api/files/:id`, `/api/zip`, `/api/quotes`, `/api/accounting/import|export`, `/api/mail/draft|preview|queue`, `/api/cron`이다. 계정·대상별 권한은 서버에서 다시 검사한다. 프런트엔드 버튼 숨김을 보안 경계로 삼지 않는다.

### 운영 연결 순서

1. 회사 소유 호스팅·Supabase·도메인·백업 저장소와 담당자를 확정한다. 현재 지속 실행 Node 24 **한 인스턴스** 기준으로 배포한다.
2. 회사 소유 Supabase에서 migration을 실행하고 Private Storage, 공개 가입 차단, Auth 리다이렉트, 대표 계정을 확인한다. `.env.example`의 서버 전용 키를 호스팅의 비밀 설정에 넣는다.
3. `APP_MODE=supabase`, 올바른 `APP_URL`, `MASTER_EMAIL`, `NODE_ENV=production`으로 실행한다. HTTPS·프록시·쿠키·재시작 후 재로그인을 확인한다.
4. 새 Supabase는 빈 업무 공간으로 시작한다. **로컬 이관 DB가 자동으로 운영에 복사되지 않는다.** 운영 반입은 대상 계정·저장 한도·백업을 정한 후 별도 검증한다.
5. 대표/직원 4계정 권한을 확정하고 UAT 대조표의 남은 범위를 실행한다. 비밀번호·service role 키는 문서/Git에 기록하지 않고 소유자가 비밀 저장소로 관리한다.
6. 알림용 Resend·인증 스케줄러와 상품 메일용 Microsoft 365를 각각 연결한다. [Microsoft 365 안내](MICROSOFT365_SETUP.md)에 따라 지정 메일함만 허용한다. 검토 모드는 실제 고객에게 발송하지 않는다.
7. 외부 비공개 백업 저장소와 일일 실행을 구성하고 새 프로젝트에서 복원한다. 실제 복구 시간과 담당자를 기록한 뒤 운영 인수를 결정한다.

## 6. 보안·SEO·장애 대응

- 내부 업무 앱의 SEO 목표는 검색 노출 방지다. 기존 noindex/nofollow와 인증 보호를 유지한다. 페이지 제목은 탭 구분을 돕는다. robots/meta는 접근 통제를 대신하지 않는다.
- Supabase 브라우저 SQL 접근과 public Storage를 열지 않는다. service role은 서버에서만 사용한다. 비공개 첨부·견적은 인증 API를 거친다. API 응답은 no-store다.
- `.env`, `.local`, 테스트 DB, 원본 이관 자료, 고객 파일, 백업, `outputs`는 Git 제외 대상이다. 공개 저장소에 올릴 데이터로 해석하면 안 된다.
- 저장 충돌(409)이면 현재 입력을 별도 복사하고 최신 내용을 확인해 다시 적용한다. 요청 시간 초과는 서버에서 이미 저장했을 수도 있으므로 조회 후 재시도한다. 메일의 불확실 발송은 무조건 재발송하지 않는다.
- 서버 재시작 시 세션이 사라져 다시 로그인한다. 여러 서버로 확장하기 전 공유 세션과 예약 작업 잠금이 필요하다.
- 구버전 PHP 사이트의 종료, 공개 파일 제거, DNS 전환·검색엔진 삭제는 이번 로컬 작업으로 실행되지 않았다. 기존 사이트의 소유자·담당자가 데이터 보존과 접근 경로를 확인해야 한다.

### 백업·복구

```powershell
npm run backup
node scripts/verify-backup.mjs backups/YYYY-MM-DD_timestamp_id
node scripts/restore-local.mjs backups/YYYY-MM-DD_timestamp_id test-results/restore-new
```

예시 경로는 실제 완료 백업 경로로 바꾼다. 복원 대상은 존재하지 않는 새 디렉터리여야 한다. 실행별 `.incomplete-*`는 실패 조사용이며 정상 완료본으로 취급하지 않는다. 최신 7개 백업 날짜의 완료본을 보관하므로 하루 여러 번 실행하면 저장 공간이 더 필요하다. DB·파일·참조·해시 검증이 모두 성공한 뒤 파일 열람과 권한까지 확인한다. 운영 Supabase 복구는 이 로컬 명령만으로 완료되지 않는다.

장애 발생 시 발생 시간·화면·오류 상태·배포 커밋을 기록하고, 먼저 백업을 확보한다. 확인되지 않은 복원본으로 현재 업무 DB를 덮어쓰지 않는다. 코드 복귀와 데이터 복구는 별개이며 이전 코드가 현재 데이터 구조를 읽는지 확인해야 한다.

## 7. 남은 개선의 우선순위

| 순서 | 작업 | 이유 |
|---|---|---|
| 운영 전 | 실제 인증/4계정/메일/복원과 미완료 UAT, 비용 미저장 확인창 실조작 | 연결 환경과 실제 사용자 흐름의 결과가 아직 없음 |
| 데이터 증가 시 | 화면별 API와 서버 페이지네이션 | 최초 JSON 약 8.88MB 및 전체 JSONB 저장 비용은 남아 있음 |
| 대용량 사용 전 | 업로드·ZIP 메모리 및 동시 처리 제한 검증 | 현재 서버 메모리 버퍼 방식과 50MB/200MB 한도의 실측 필요 |
| 사용 피드백 후 | 모바일 대시보드 재배치, 트리 키보드 탐색, 도움말 | 기존 가벼운 UI 유지와 실제 불편의 우선순위에 따라 선택 |
| 유지보수 시 | 큰 화면 파일 분리, 선택적 이관 도구 아카이브 | 동작·증빙을 잃지 않는 범위에서 진행. 과거 코드 일괄 삭제 금지 |

이번 작업에서 새 프레임워크·공개 SEO·외부 유료 서비스를 추가하지 않았다. 상세 성능 전후 수치와 선택 개선 목록은 [개선 결과](점검_개선결과_2026-09-23.md)에 보존한다.

## 8. 인수 시 필요한 정보

원격 Git 저장소 URL, 운영 호스팅/도메인 담당, 회사 소유 Supabase와 대표·직원 이메일, 정식 견적 양식, Microsoft 365/알림 발신 설정, 백업 저장소·복구 담당 및 장애 연락 체계가 필요하다. 비밀키·비밀번호는 이 문서에 기입하지 않는다. 작성 시점에 Git 원격 주소는 미등록이며, 로컬 커밋과 원격 푸시 완료 여부를 구분해 인계한다.
